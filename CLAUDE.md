# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A classic Tetris implementation in vanilla JavaScript, HTML5 Canvas, and CSS. No dependencies, no build step, no `package.json`. The entire game lives in three files:

- `index.html` — DOM structure: the main `<canvas id="board">` (300×600, 10×20 grid of 30px blocks), the `<canvas id="next-canvas">` preview, HUD elements (`#score`, `#lines`, `#timer`, `#level`, `#combo`, `#energy-fill`), the mode/theme/sound toggle buttons, and the overlay (start screen / pause / game-over / challenge-result, see **Local high scores and the start screen** below).
- `style.css` — dark/retro arcade visual theme.
- `game.js` — all game logic, rendering, effects and audio (single file, no modules).

## Running the game

There's no build/test/lint tooling. Just serve or open the files directly:

```bash
# Open directly
start index.html       # Windows

# Or serve locally (any static server works)
python3 -m http.server 8000
npx serve .
```

Then open in a browser (or `http://localhost:8000` if serving). To verify changes, open `index.html` in a browser and play — there is no automated test suite.

## Architecture

Everything is global state and top-level functions in `game.js` — no classes, no modules, no build step. Key pieces:

- **Board model**: `board` is a `ROWS × COLS` matrix; each cell is `0` (empty) or an index 1–8 into `COLORS`/`PIECES` identifying which piece locked there.
- **Pieces**: `PIECES` defines each piece as a square matrix of color indices: the 7 classic tetrominoes, an 8th challenge piece, the "nut" (`NUT = 8`) — a 3×3 ring (`[[8,8,8],[8,0,8],[8,8,8]]`) with an empty center that can never be filled by another piece, permanently blocking that row from being cleared (unless the row above it clears first, exposing the hole from above so a later piece can fill it) — and a 9th power-up piece, the "bomb" (`BOMB = 9`, shape `[[9]]`, see **Bomb piece** below). `current` and `next` are `{ type, shape, x, y }` objects; `randomPiece()` picks uniformly among the 8 tetromino/nut types (`Math.floor(Math.random() * 8) + 1`) except when a bomb is due (see below).
- **Nut holes rendering**: `holes` is a render-only `ROWS × COLS` matrix (parallel to `board`, kept in sync in `merge()`, `clearLines()`, `explode()`, `zapBottomRow()`, and `collapseColumn()`) marking which locked cells are a nut's empty center, so `draw()`/`drawNext()` can paint a circle there via `drawNutHole()`. It never participates in collision or line-clear logic — `board` alone is the source of truth for those.
- **Bomb piece**: `linesUntilBomb` counts down as lines clear; when it reaches 0, `randomPiece()` returns a `BOMB` piece instead of a random tetromino/nut and re-rolls `linesUntilBomb` via `bombInterval()` (a random gap of `BOMB_MIN_LINES`–`BOMB_MAX_LINES` lines). A bomb is a `1×1` piece that falls and is moved/rotated like any other, but `lockPiece()` never `merge()`s it into `board` — instead it calls `explode(x, y)`, which zeroes out the 3×3 area centered on the bomb (clearing both `board` and `holes` there), scores `destroyed * BOMB_BLOCK_SCORE * level` for the blocks it removed, and calls `collapseColumn(c)` on every touched column so blocks above the gap fall to fill it (an in-place gravity pass, distinct from `clearLines()`'s whole-row splice). Because the bomb is consumed by `explode()` rather than `merge()`, `lockPiece()` passes `isBomb` as `clearLines(neutralTurn)`'s argument so a bomb that clears no lines doesn't reset `combo`.
- **Rotation**: `rotateCW(shape)` transposes + reverses rows. `tryRotate()` applies it and, on collision, attempts wall kicks via `kicks = [0, -1, 1, -2, 2]` (small horizontal offsets) before giving up.
- **Collision**: `collide(shape, ox, oy)` checks board bounds and overlap with locked cells — the single source of truth used by movement, rotation, and drop logic.
- **Game loop**: `loop(ts)` runs via `requestAnimationFrame`, accumulates elapsed time in `dropAccum`, and advances the piece down one row (or locks it) once `dropAccum >= dropInterval`.
- **Locking a piece**: `lockPiece()` → `merge()` (writes the piece into `board`) → `clearLines(neutralTurn)` → (if the challenge was just won, `clearLines()` already set `gameOver` and `lockPiece()` returns without spawning) → if the energy bar is full and the bottom row isn't already empty, `zapBottomRow()` fires (see **Energy bar** below; another `gameOver` check follows, since the zap can itself win the challenge) → `spawn()` (promotes `next` to `current`, generates a new `next`; if the new piece immediately collides, calls `endGame()`). `neutralTurn` is `true` when the locked piece was a `BOMB`, so an empty-landing bomb doesn't break the combo streak.
- **Line clearing / scoring**: `clearLines()` scans bottom-up, splicing out full rows and unshifting empty ones at the top. Score uses `LINE_SCORES = [0, 100, 300, 500, 800]` multiplied by `level` and by `comboMultiplier()`; hard drop adds 2 pts/row dropped, soft drop adds 1 pt/row (neither is affected by the combo). `level` increments every 10 lines, and `dropInterval = max(100, 1000 - (level - 1) * 90)` ms. The challenge win check lives in `checkChallengeWin()` (`lines >= CHALLENGE_LINES`), called from both `clearLines()` and `zapBottomRow()` since either can grow `lines`.
- **Chained combo**: `combo` counts consecutive piece placements that cleared at least one line; `comboMultiplier()` returns `min(combo, COMBO_MAX)` (capped at x10) and scales line-clear score. Locking a piece that clears nothing resets `combo` to 0 — except a `BOMB` landing empty, which is a neutral turn that preserves the streak. `comboFx` drives a fading "COMBO xN" overlay on the board (`draw()`) once `combo >= 2`; the HUD's `#combo-section` gets a `combo-active` class for the same condition.
- **Ghost piece**: `ghostY()` projects `current`'s landing row by repeatedly testing `collide` downward; drawn at `globalAlpha = 0.2`.
- **Rendering**: `draw()` clears the canvas, applies the screen-shake translation (if `shake` is active) inside a `ctx.save()`/`ctx.restore()` pair, then redraws the grid, locked board, ghost piece, and current piece every frame onto `#board`; `drawNext()` renders the preview piece onto `#next-canvas`. Because `draw()` has a mid-function `if (gameOver) return`, that early exit also calls `ctx.restore()` first so the save/restore stack never leaks. `cssVar(name, fallback)` caches `getComputedStyle` lookups for theme colors used while drawing (nut holes, grid lines, combo/banner text); `applyTheme()` clears the cache so a theme switch is picked up on the next frame.
- **Input**: a single `keydown` listener calls `unlockAudio()` first (any key is a valid gesture to unlock/resume the `AudioContext`), then handles `KeyM` (mute toggle, works even while paused/game-over — see below), `KeyP` (pause, same), arrows (move/soft-drop), `ArrowUp`/`KeyX` (rotate), `Space` (hard drop). Movement/rotation sounds only fire when the action actually succeeds (`tryRotate()` now returns `true`/`false` for this).

## Visual effects

All effects below are **render-only state** — like `holes`, none of them are read by `collide()`, scoring, or any other gameplay logic, and a bug in them cannot affect the board:

- `particles` (array of `{x, y, vx, vy, life, maxLife, color, size}`), `flashes` (array of `{row, t}`), `banner` (single `{text, t, color}` or `null`), and `shake` (single `{t, dur, mag}` or `null`) are ticked every frame in `tickEffects(dt)` (called from `loop()`, right after `animClock += dt`) and rendered in `draw()`. They follow the same `{t}`-accumulator idiom already used by `blast`/`comboFx`.
- `clearLines()` captures each full row's index **and a copy of its color values** (`board[r].slice()`) *before* splicing it out — the splice/unshift immediately destroys that row's position in `board`, so this is the only point where the flash/particle color/position can be read.
- **Line clear**: each cleared row gets a white `flashes` entry plus a handful of `spawnLineParticles` in the row's own color. 1–3 lines play `SFX.clear(n)`; 4 lines (`cleared >= 4`) instead play `SFX.tetris()`, show a "¡TETRIS!" `banner`, and trigger a bigger `shakeScreen`.
- **Combo**: unchanged `comboFx` mechanism, but the popup now pops in with a scale easing and shifts color by multiplier tier (amber → orange → pink → cyan at x10). `pulseCombo()` removes then re-adds the `combo-active` class (forcing a reflow in between) so the CSS `combo-pulse` keyframe replays on every multiplier increase — previously it only played once, since re-toggling an already-present class doesn't restart a CSS animation.
- **Level up**: `clearLines()` captures `prevLevel` before recomputing `level`; if it went up, shows a "NIVEL N" banner and plays `SFX.levelUp()`.
- **Bomb**: `explode()` keeps the existing `blast` ring, adds `SFX.bomb()`, a strong `shakeScreen`, and a burst of `spawnParticles` at the blast center.
- **Hard drop**: small `shakeScreen` + `SFX.hardDrop()`.
- **Screen shake**: `shakeScreen(mag, dur)` sets/replaces `shake` (a stronger shake in flight is never downgraded by a weaker one). `draw()` wraps its whole body in `ctx.save()`/translate-by-shake/`ctx.restore()`, but the initial `ctx.clearRect()` happens *before* the translate (in identity transform) so the full canvas is always cleared — the board's opaque background comes from CSS (`#board { background: var(--board-bg) }`), so the sliver revealed at an edge during a shake reads as the board jolting, not as a rendering artifact.
- HUD: `updateHUD()` also toggles a `combo-hot` class (`combo >= 5`) for a stronger glow at high combo tiers.

## Challenge mode

The game has two modes, held in the module-level `mode` variable (`MODE_CLASSIC` | `MODE_CHALLENGE`), persisted to `localStorage` (`MODE_STORAGE_KEY = 'tetris-mode'`) and applied by `applyMode(m)`/`initMode()` — the same pattern as `applyTheme`/`initTheme`. Classic is unchanged and is the default. Challenge mode plays with identical rules (levels, speed, bomb, nut, combo, scoring) but adds a win condition: clear `CHALLENGE_LINES` (40) lines before `CHALLENGE_TIME_MS` (2 minutes) runs out.

- **Toggle**: the `#mode-toggle` HUD button (or the `C` key, handled in the `keydown` listener above the pause/gameOver guard, like `KeyM`/`KeyP`) calls `toggleMode()`, which flips `mode`, persists it, and calls `init()` to restart. `init()` does **not** take a mode parameter — it reads the module-level `mode` — so its two call sites (`restartBtn`, boot) are unchanged. The button click handler calls `.blur()` before toggling, since the `keydown` listener lives on `document` and a focused button would otherwise let `Space`/`Enter` re-trigger it.
- **Countdown**: `timeLeft` (ms) is decremented in `loop()` by the same `dt` used for `dropAccum`/`animClock`, right after `animClock += dt`. Because `dt` comes from `requestAnimationFrame` deltas and `lastTime` is re-seeded on unpause and in `init()`, the countdown automatically freezes during pause — no extra bookkeeping needed. `updateTimer()` formats `timeLeft` (via `formatClock`) and writes to `#timer` only when the displayed second actually changes (`lastTimerText`), and toggles `timer-warn`/`timer-critical` classes on `#timer-section` at `CHALLENGE_WARN_MS`/`CHALLENGE_CRITICAL_MS`. It's called from `loop()`, `init()`, and `finishChallenge()` — never from `updateHUD()`, which fires on every keypress and would update it at an irregular cadence.
- **Win**: detected in `checkChallengeWin()` (`lines >= CHALLENGE_LINES`), called at the end of `clearLines()` and of `zapBottomRow()` — the only two places `lines` grows, so it catches normal clears, bomb-triggered clears, and the energy-bar zap. Sets a "¡GANASTE!" `banner` and calls `finishChallenge(true)`.
- **Loss**: detected in `loop()`, immediately after the drop/lock block and guarded by `!gameOver` — this ordering means that if the timer hits zero the same frame a piece locks and clears the 40th line, the win (set synchronously inside `lockPiece()` → `clearLines()`, earlier in the same `loop()` call) already set `gameOver = true`, so the loss check is skipped. The player wins ties.
- **Shared teardown**: `stopRun()` (freeze `gameOver`/`paused`, cancel the rAF, draw one final frame) and `showOverlay(title, detail, won)` (set `#overlay-title`/`#overlay-score` text, toggle `overlay-win` on the title, unhide `#overlay`) are used by all three terminal paths — `endGame()`, `finishChallenge(won)`, and `togglePause()` (pause reuses `showOverlay('PAUSA', '', false)`, which also clears any leftover `overlay-win` class from a previous win). `finishChallenge()` shows elapsed time (`formatElapsed`) on a win or `lines / CHALLENGE_LINES` on a loss, plus the final score in both. No parallel "run stopped" flag was introduced — everything still gates on `gameOver`, so the six pre-existing guard sites (`loop`'s two returns, the `keydown` guard, `draw()`'s early return, `endGame()`'s reentrancy guard, `togglePause()`'s guard) keep working unchanged.
- **HUD**: `#lines` shows `"N / 40"` in challenge mode (`updateHUD()`), plain `N` in classic. `#timer-section` is hidden via CSS (`body:not(.mode-challenge) #timer-section`) rather than toggled from JS.

## Energy bar

Unlike `combo` (which resets on any empty clear), the energy bar is a persistent-through-the-run resource that fills as the player clears lines and, once full, automatically fires an ability: **wipe the bottom row**. Like `combo` (and unlike `holes`/`particles`/etc.), `energy`/`energyReady` are **gameplay state** — they gate a board mutation — while `energyFx` (the on-canvas sweep animation) is render-only, following the same `{t}`-accumulator idiom as `blast`/`comboFx`.

- **Filling**: inside `clearLines()`'s `if (cleared)` block, right after `dropInterval` is recomputed, `energy` gains `ENERGY_GAIN[cleared]` (`[0, 10, 25, 45, 70]` — bonus for multi-line clears, capped at `ENERGY_MAX = 100`) as long as `!energyReady`. Reaching `ENERGY_MAX` sets `energyReady = true` and plays `SFX.energyFull()`. Gaining stops while `energyReady` is true so a pending zap can't be "overfilled".
- **Firing**: the ability does **not** fire inside `clearLines()` — that function is mid-mutation on `board`/`holes` (splicing rows) and may have already ended the game via `checkChallengeWin()`. Instead, `lockPiece()` checks `energyReady` right after `clearLines()` returns and `gameOver` is confirmed false: if the bottom row (`board[ROWS - 1]`) has any block, it resets `energy`/`energyReady` to 0/false and calls `zapBottomRow()`, then re-checks `gameOver` (the zap can itself finish the challenge) before `spawn()`. If the bottom row is already empty, the full bar is left `energyReady` (and pulsing in the HUD) waiting for a piece to touch that row.
- **`zapBottomRow()`** (next to `explode()`, the existing template for "ability that mutates the board"): splices out the bottom row and unshifts an empty one at the top (same technique as `clearLines()`, capturing `board[row].slice()` for particle color before the splice), adds `destroyed * BOMB_BLOCK_SCORE * level` to score, increments `lines` by 1 (so it can trigger a level-up or a challenge win) and `dropInterval` accordingly, pushes a `flashes` entry + `spawnLineParticles`, sets `energyFx = { t: 0 }`, shakes the screen (`SHAKE_ZAP`), and plays `SFX.zap()`. It shows a "NIVEL N" banner on level-up, or a "¡ZAP!" banner otherwise — but only `if (!banner)`, since the single `banner` slot may already hold a "¡TETRIS!" from the `clearLines()` call that filled the bar moments earlier. It deliberately does **not** touch `energy` or `combo` — the ability can't re-trigger itself or inflate the combo streak.
- **HUD**: `updateHUD()` writes `#energy-fill`'s `style.width` as a `%`, memoized through `lastEnergyPct` (same anti-repeat-write pattern as `updateTimer()`'s `lastTimerText`, since `updateHUD()` runs on every keydown), and toggles `energy-ready` on `#energy-section` for the pulsing "ability ready" glow.
- **Render**: the `energyFx` sweep is drawn in `draw()` just before the `blast` block (so it's still visible on the final game-over frame, since it sits above the `if (gameOver) return`) — a glowing bar across the bottom row that shrinks and fades over `ENERGY_FX_DURATION`. It's ticked in `tickEffects(dt)` alongside `flashes`/`banner`/`shake`.
- Persistence: `energy`/`energyReady`/`energyFx`/`lastEnergyPct` are reset in `init()` like `combo`/`comboFx` — this is per-run state, **not** persisted to `localStorage` (unlike theme/mode/sound).

## Audio

Entirely synthesized with the Web Audio API — no audio files, no `<audio>` tags, no dependencies:

- `unlockAudio()` lazily creates a single `audioCtx`/`masterGain` pair on first use and calls `resume()` if suspended; it's invoked from the `keydown` listener and every button click (`restartBtn`, `themeToggle`, `soundToggle`) since browsers require a user gesture to start/resume an `AudioContext`. If the browser has no `AudioContext`, `unlockAudio()` no-ops and every `SFX.*` call becomes a silent no-op — the game never depends on audio.
- `tone(opts)` is the one primitive behind almost every sound: an `OscillatorNode` with an exponential attack/decay `GainNode` envelope (avoids clicks), disconnected from the graph in `onended` (no node leaks). `noise(opts)` is the same idea with a cached white-noise `AudioBufferSourceNode` through a swept lowpass filter, used for the bomb and the hard-drop thud. Both are guarded by a `voices` counter capped at `MAX_VOICES` so rapid key-repeat can't stack into distortion; `throttled(key, fn)` additionally rate-limits `move`/`rotate`/`softDrop` to `MOVE_SFX_THROTTLE` ms apart.
- `SFX` is a plain object of fire-and-forget functions (`move`, `rotate`, `softDrop`, `hardDrop`, `lock`, `clear(n)`, `tetris`, `combo(mult)`, `levelUp`, `win`, `timeUp`, `bomb`, `energyFull`, `zap`, `gameOver`) — `SFX.combo(mult)` is the pitch-rises-with-the-streak signature sound; `SFX.win()`/`SFX.timeUp()` are the challenge-mode victory fanfare and time-out sound; `SFX.energyFull()`/`SFX.zap()` are the energy-bar chime and bottom-row-wipe sound (built from `tone()`/`noise()` like `levelUp()`/`bomb()`). None of them ever `await` or block the game loop.
- Mute: `setMuted(v)` sets `masterGain.gain.value` and persists to `localStorage` (`SOUND_STORAGE_KEY = 'tetris-muted'`); `initSound()` restores it at boot, mirroring the existing `applyTheme`/`initTheme` pattern. Toggled by `KeyM` (works even while paused/game-over, like `KeyP`) or the `#sound-toggle` HUD button.

## Local high scores and the start screen

The game no longer auto-starts a run on page load: it shows a start screen first (records, a mode picker, a JUGAR button), and the same records box also appears on the game-over/result screen, with a name-entry form when a run qualifies for the top 5.

- **`init()` vs `resetRunState()`**: `init()` used to do everything; it's now split. `resetRunState()` holds everything that resets per-run state (board, holes, score, combo, energy, effects, `pendingRecord`, hiding `#new-record-box`) but does **not** spawn a piece, start the rAF loop, or touch the overlay. `init()` calls `resetRunState()`, sets `started = true`, then spawns the first piece and starts the loop, exactly like the old `init()` did after its setup. `restartBtn`'s click handler is unchanged (`init()`).
- **`showStartScreen()`**: calls `resetRunState()`, sets `started = false` and `gameOver = true` (reusing every existing `gameOver` guard — `draw()`, the `keydown` listener, `lockPiece()`, etc. — to keep the board frozen and empty), sets `current = null; next = null;`, draws one empty frame, then shows `#panel-start` and calls `renderRecords()`. Because `current`/`next` can be `null` here, `draw()`'s mid-function early exit is `if (gameOver || !current) return` (still preceded by `ctx.restore()`) and `drawNext()` starts with `if (!next) return;`.
- **Two overlay panels, not a generic system**: `#overlay` holds `#panel-start` (visible by default) and `#panel-result` (wraps the pre-existing `#overlay-title`/`#overlay-score`/`#restart-btn`, plus the new record-form/records box). `showOverlay(title, detail, won)` hides `#panel-start` and shows `#panel-result` before setting the title/detail text, so it works for game over, challenge finish, **and** the unchanged `togglePause()` (which still just calls `showOverlay('PAUSA', '', false)` — pause was deliberately left untouched, so it displays as a bare "PAUSA" text in the result panel, exactly as it looked in the plain one-panel overlay before this feature).
- **Records storage**: `scores` is `{ classic: {top:[], bestCombo, bestLines}, challenge: {...} }`, persisted as JSON under `SCORES_STORAGE_KEY = 'tetris-scores'`. `loadScores()` wraps `JSON.parse` in try/catch — a corrupted or missing value falls back to `emptyScores()` rather than breaking boot. `initRecords()` loads it at boot; `resetRecords()` (wired to `#start-reset-records-btn`, behind a `confirm()`) replaces it with `emptyScores()`, saves, and re-renders.
- **Submitting a run**: `offerRecord()` runs at the end of both `endGame()` and `finishChallenge()`. It calls `submitRun({score, lines, combo: maxCombo})`, which updates the current mode's `bestCombo`/`bestLines` **unconditionally** (even for a run that doesn't make the top 5 — a record streak or line count is worth keeping on its own) and returns the rank the score would take in the top 5 (computed as how many existing entries already score at least as high, which is exactly where it will land after `insertScore()`'s sort) or `-1` if it doesn't qualify. On `-1`, the name form stays hidden. Otherwise `pendingRecord = {entry, rank}` is stashed, the name form (prefilled from `LAST_NAME_STORAGE_KEY`) is shown and focused. Submitting `#new-record-form` reads/trims/uppercases/truncates the name to 8 characters (`'---'` if empty), calls `insertScore({...pendingRecord.entry, name})` (which pushes into the mode's `top`, sorts by score descending, truncates to `TOP_SCORES_MAX`, saves, and remembers the name), then re-renders with that rank highlighted.
- **`maxCombo`**: tracks the highest `combo` reached during the run (`clearLines()` updates it right next to `combo++`), independent of `combo` itself resetting on an empty clear. Reset to 0 in `resetRunState()`.
- **Rendering records**: `renderList(listEl, top, highlightRank)` fills one `<ol>` (an empty-state message if `top` has no entries; each row's player name is HTML-escaped via `escapeHtml()` before being injected, since it's read back from `localStorage` and rendered via `innerHTML`). `renderRecords(highlightRank)` calls it for both the start screen's and the result panel's lists/best-combo/best-lines, and is called after every mutation (`resetRecords()`, `offerRecord()`, the name-form submit) and whenever the start screen is shown.
- **Mode switching**: `setMode(m)` (the single place that changes `mode`) persists it, calls `applyMode(m)`, then `init()` if `started` else `showStartScreen()` — so picking a mode from the start screen (via `#start-mode-select` or `toggleMode()`, which now just calls `setMode(...)`) only refreshes that screen's records for the new mode instead of starting a game.
- **`isTyping(el)`**: returns true for `INPUT`/`SELECT`/`TEXTAREA`/`contenteditable` targets. Checked first thing in the `keydown` listener, before `unlockAudio()`/`KeyM`/`KeyP`/`KeyC` — without it, typing a player name could trigger mute/pause/mode-switch on any keystroke that happens to match those letters.
- **Boot sequence**: `resetRunState()` runs once up front (so `board`/`holes`/`particles`/etc. exist before `showStartScreen()`'s first `draw()`), then `initTheme(); initSound(); initMode(); initRecords(); showStartScreen();` — replacing the old direct `init()` call.

## Tunable constants (in `game.js`)

`COLS`, `ROWS`, `BLOCK` (cell size px), `COLORS`, `LINE_SCORES`, `dropInterval` (initial fall speed), `COMBO_MAX` (combo multiplier cap), `COMBO_FX_DURATION` (ms the "COMBO xN" overlay stays visible), `BOMB_MIN_LINES`/`BOMB_MAX_LINES` (line-clear gap between bombs), `BOMB_BLOCK_SCORE` (score per block destroyed by a bomb or a zap), `BLAST_DURATION` (ms the bomb ring animation lasts), `MASTER_VOLUME`, `MAX_VOICES`, `MOVE_SFX_THROTTLE` (audio), `MAX_PARTICLES`, `FLASH_DURATION`, `BANNER_DURATION`, `PARTICLE_GRAVITY`, `SHAKE_HARD_DROP`/`SHAKE_TETRIS`/`SHAKE_BOMB`/`SHAKE_ZAP` (visual effects), `ENERGY_MAX` (bar capacity), `ENERGY_GAIN` (per-clear gain, indexed by lines cleared at once), `ENERGY_FX_DURATION` (ms the zap sweep animation lasts) (energy bar), `CHALLENGE_LINES` (line goal), `CHALLENGE_TIME_MS` (time limit), `CHALLENGE_WARN_MS`/`CHALLENGE_CRITICAL_MS` (HUD timer warning thresholds) (challenge mode), `TOP_SCORES_MAX` (records kept per mode) (local high scores). If `COLS`/`ROWS`/`BLOCK` change, update the `#board` canvas `width`/`height` in `index.html` to match (`COLS × BLOCK` by `ROWS × BLOCK`).
